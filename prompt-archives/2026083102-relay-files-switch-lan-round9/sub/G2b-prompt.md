## Reviewer finding (verified blocker)
G2 removed the fixed 450ms delay and now sends `LIVE_RESUME` right after the TERM_HISTORY send returns `sent` (`switch-barrier.ts` ~line 231). But `DataChannelCarrier.send()` (`apps/gateway/src/mesh/rtc/data-channel-carrier.ts` ~line 112) fragments frames into 64 KiB pieces and returns `sent` after only the FIRST fragment was accepted while the rest sits in `remainder`. So for a >64 KiB history over a DataChannel-backed session (browser terminal reaching a remote node via the mesh), the immediately following `LIVE_RESUME` send hits `remainder` and returns `backpressure`. `sendLiveResume()` has already switched the transaction to LIVE / stopped output buffering, and on send failure it completes the transaction → the client never receives LIVE_RESUME (stays ACKED/HISTORY_APPLIED), the send guard stays backpressured and the carrier is eventually terminated (gap/timeout). The old 450ms delay masked this by letting the remainder drain.

## Deliverable
1. Make the history → LIVE_RESUME sequence drain-aware: only stop output buffering / complete the transaction once LIVE_RESUME has actually been accepted by the carrier. If the send returns backpressure, keep buffering, wait for the carrier's drain notification (find the existing drain/onDrain hook the carriers expose — do not poll with timers if a drain callback exists; if none exists for DataChannelCarrier, add one consistent with the WebSocket path), then retry LIVE_RESUME with the same token guard (stale token → abort silently). Keep the existing history/ACK timeout fallbacks as the last resort.
2. Fix the DataChannel send contract so callers can distinguish "whole frame accepted" from "only partially queued": either return `backpressure`-style status when a remainder is left (and drain-flush it internally), or expose a `pending/flushed` signal — pick what fits the existing WebSocket carrier semantics and document it in the result file. Do not change wire framing.
