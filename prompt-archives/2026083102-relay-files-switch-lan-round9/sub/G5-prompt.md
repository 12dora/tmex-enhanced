## Goal (user requirement, verbatim intent)
"Like a BIOS upgrade: the old version must not be taken out of service until the new version is online and verified; and a failed/interrupted upgrade must not leave garbage behind." Power loss or SIGKILL at ANY instant must leave the machine with a bootable, consistent install (old or new), and the next `upgrade`/boot must be able to finish or clean up.

## Target design (implement exactly; keep it as small as it can be while meeting the goal)
Layout under `<installDir>`:
```
versions/<version>/{cli,runtime,resources,native}   # immutable per version
current -> versions/<version>                        # symlink, switched with atomic rename (create `current.tmp` symlink then rename over `current`)
staging/<txnId>/                                     # download+extract, same filesystem as versions/
backups/<txnId>/{tmex.db,tmex.db-wal,tmex.db-shm}    # DB snapshot for rollback
upgrade-state.json                                   # journal (atomic write via temp+rename+fsync): {txnId, phase, fromVersion, toVersion, startedAt, updatedAt, dbBackup, error?}
upgrade.lock                                         # O_EXCL lock file containing pid+startedAt; stale if pid dead
data/ app.env run.sh install-meta.json               # unchanged locations
```
`run.sh` (stable path; unit/plist keep pointing at it) resolves everything through `current`: `TMEX_FE_DIST_DIR=<installDir>/current/resources/fe-dist`, `TMEX_MIGRATIONS_DIR=<installDir>/current/resources/gateway-drizzle`, `TMEX_NATIVE_DIR=<installDir>/current/native`, `exec bun <installDir>/current/runtime/server.js`. The shims (`~/.local/bin/tmex`, `~/.bun/bin/tmex`) point at `<installDir>/current/cli/bin/tmex.js`; write them atomically (temp + rename; no rm-then-symlink gap).

Upgrade phases (each phase transition = journal write; the journal is the source of truth):
1. `lock` — take `upgrade.lock` (fail fast with a clear message if another upgrade is running; reclaim if the pid is dead).
2. `staging` — download the tarball into `staging/<txn>/` (same filesystem), verify: HTTP ok, tar extracts, `package/package.json` version equals the requested version, layout check (`resolvePackageLayout`), and **sha256 against the release's `SHA256SUMS` asset when present** (add generation of `SHA256SUMS` to `.github/workflows/release.yml` for future releases; when the asset is absent — older releases — log that integrity is unverified and continue). Extract to `staging/<txn>/pkg`, then `rename` into `versions/<toVersion>` (if that dir already exists from a previous interrupted run, remove it first — it is garbage by definition unless it is the `current` target).
3. `preflight` — start the candidate runtime from `versions/<toVersion>` on an ephemeral port bound to 127.0.0.1 with `DATABASE_URL` pointing at a **copy** of the DB (checkpoint the live DB first if possible: `PRAGMA wal_checkpoint(TRUNCATE)` via `bun:sqlite` opened read-write is acceptable, else copy db+wal+shm together), same app.env otherwise (override port/bind/base-url/DB path/`TMEX_ROLES`? keep roles but the candidate must NOT connect to the hub/mesh or open the peer port — set env to disable mesh/uplink for preflight: find the existing env switches, e.g. `TMEX_ROLES=standalone` or a dedicated `TMEX_PREFLIGHT=1` flag you add to the gateway runtime that skips mesh/uplink/peer-server/tunnel startup; if you add a flag, keep it minimal and documented). Poll `/healthz` (add `version` to the healthz JSON in `system-routes.ts` using the build-time version constant already used for the node inventory version — grep `inventory` / `TMEX_MONOREPO_VERSION`) until `status==='ok' && version===toVersion` (timeout 60s), then stop the candidate and delete its DB copy. Preflight failure ⇒ abort: delete `versions/<toVersion>` and staging, journal `aborted`, old service was never touched.
4. `backup` — stop the service (verify the process is gone: poll pid/port), then copy `tmex.db{,-wal,-shm}` to `backups/<txn>/` (fsync), journal `switching`.
5. `switch` — atomic `current` rename to `versions/<toVersion>`; rewrite `run.sh` atomically only if its content changed (it is version-independent now); journal `started`; start the service; health check `/healthz` on the real port: `ok` + `version===toVersion`, timeout 60s.
6. On success: write `install-meta.json` atomically (version, updatedAt), journal `committed`, then **garbage collection**: delete `staging/<txn>`, `backups/<txn>` (keep the backup only if `--keep-backup`), and prune `versions/*` down to `current` + one previous last-known-good; also remove the legacy top-level `cli/ runtime/ resources/` dirs once they are no longer referenced (see migration below).
7. On failure after switch (health check fails or service won't start): stop the service, restore the DB three files from `backups/<txn>`, switch `current` back to `fromVersion`, start the old service, verify its health, journal `rolled_back` with the error, keep `versions/<toVersion>` deleted (garbage-free) — print a clear message.
8. Crash recovery: `upgrade` (and a new `tmex upgrade --repair`, also invoked automatically at the start of every `upgrade`/`init`) reads the journal: `staging`/`preflight` ⇒ delete staging + candidate dir; `switching` (service stopped, current still old) ⇒ start old service, clean; `started` (current=new, not committed) ⇒ run the health check now and either commit or roll back; `committed`/`rolled_back`/`aborted` ⇒ only cleanup leftovers. Everything idempotent. The stale lock is reclaimed when the pid is dead.

Legacy install migration (existing machines have `cli/ runtime/ resources/ native/` at top level and `run.sh` pointing at them): the first apply on such a layout performs a crash-safe conversion BEFORE the upgrade: copy the existing top-level dirs into `versions/<fromVersion>/` (fromVersion from `install-meta.json`; abort with a clear message if missing), create `current` atomically, rewrite `run.sh` atomically to the `current`-based content, rewrite shims; the running old service keeps using the old files until its next restart (both trees are identical). Only after the upgrade is `committed` are the legacy top-level dirs deleted. `init` (fresh install) writes the new layout directly.

`direct.ts` (native datachannel install/remove): the native dir must live in `versions/<v>/native` (i.e. `<installDir>/current/native` at runtime) — adapt its staging/rename to operate on the resolved current version dir. `apps/gateway/src/system/upgrade.ts` (web-triggered detached upgrade): make its stage dir live under `<installDir>/staging/<txn>` instead of `mkdtemp`, and rely on the CLI's journal for cleanup; remove the in-memory-only assumption where it matters.
