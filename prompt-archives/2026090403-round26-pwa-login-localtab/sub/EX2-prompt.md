# EX2 — "Failed to load device" for remote nodes when the entry site is a relay,node

Production setup (all nodes 1.1.27): node B = https://tmexhub-sh.jiefakj.com runs roles `relay,node` (it hosts the public relay AND is itself a mesh node). Other nodes (`jiefa-app`, `jiefa-dns-1`, `konata-mac` (a macOS laptop behind NAT), `tmex` (= the former hub A, now a pure `node`), `docker-node`) are pure nodes attached to that relay. When the user opens B in the browser/PWA and clicks the devices of the other nodes, the devices page shows "failed to load device" for jiefa-app / jiefa-dns-1 / konata-mac / tmex (docker-node may or may not work — the user did not mention it). When the user opens their local entry (konata-mac, relay mode, `/n/<id>/api/devices`) everything works.

Task: trace the full request path for loading a remote node's devices from a `relay,node` entry and find why it could fail specifically on B.

1. Frontend: find the "Failed to load device" string (i18n key) and the call site (packages/stores or apps/fe devices page) — which API is called for a remote node (`/n/<nodeId>/api/devices`? `/api/mesh/nodes/:id/devices`? WS?), how the node list is obtained (`/api/mesh/nodes`, `/api/mesh/relay/status`), how the entry decides a node is "self" vs remote, and how the error is surfaced (does it swallow the HTTP status/code? we want the real reason shown).
2. Backend (apps/gateway): the `/n/:nodeId/*` proxy route — how a request is forwarded when the entry is in relay mode (uplink / relay client / mux streams over the relay, `apps/gateway/src/relay/*`, `src/mesh/*`, `src/uplink/*`), how the node id is resolved (peer cache, `nodes` table, relay member table), and how the entry authenticates to the target node (canonical HELLO / node certs / sealed pack / session forwarding). Now consider the special case where the entry node is ALSO the relay server (`relay,node`): does the relay client on B connect to its own relay via loopback (`TMEX_RELAY_URL` / mesh_relays row pointing at its own public URL — the R1 review mentioned "run.sh loopback publish")? Are streams to other members routed through the in-process relay correctly (relay-stream-router)? Is there any code path that assumes "if I am the relay then the target is local" or that dedups the local node id incorrectly (`localNodeId` handling), or that treats members of the relay as not-yet-admitted (`admission_status`, pending)? Also check per-node auth: when B forwards `/n/<id>/api/devices` does it need a session/cert for the target node that B might lack (e.g. sealed pack not uploaded on B, `peer_cache` cert missing → the "version gate" or "cert not cached" fail-closed paths from round 25)?
3. Look for any recent changes (git log -p for last ~15 commits touching apps/gateway/src/relay, src/mesh, src/uplink, packages/api-client, packages/stores devices) that could break `relay,node` entries specifically.
4. List the exact log lines / API endpoints I can call on B (with a logged-in session) to confirm the diagnosis (e.g. `GET /api/mesh/relay/status`, `GET /api/mesh/nodes`, `GET /n/<id>/api/devices` and what error codes they'd return in each failure mode).

Report: the most likely root cause(s) ranked, evidence, and the concrete fix for each.
