# EX3 — inventory of Settings → 多节点互联 → 本机 tab, and available relay/perf metrics for a redesign

The Settings page has a "多节点互联" (multi-node mesh) section with tabs; the "本机" (local machine / this node) tab has become a cluttered pile of redundant fields, hints and buttons with no logical grouping. It will be fully redesigned. Also, for nodes with the `relay` role, more performance monitoring should be displayed (modern, beautiful — think small stat tiles / sparklines).

Produce a complete inventory to drive the redesign:

1. Locate the component(s) rendering the 本机 tab (apps/fe settings routes, `packages/panels`, `packages/ui`), list every sub-component/card/section in render order, and for each: the fields shown (with i18n key + zh-CN text + en text), the data source (API endpoint + store field), the actions/buttons (and API they call), conditional visibility (by role: standalone / hub / node / relay / relay,node / hub,node; by mode: hub mode vs relay mode; by state: attached / pending / readmitPending etc.), and hint/help texts. Flag anything that is (a) duplicated across cards, (b) legacy from the hub-era that no longer applies to relay-mode nodes, (c) debug-ish internal IDs (node id, tenant id, epoch, seq…) that a normal user does not need or that could be collapsed into a "details" disclosure, (d) hint texts that restate the obvious.
2. List the backend APIs feeding it: `/api/local/*`, `/api/mesh/relay/status`, `/api/mesh/nodes`, `/api/setup/*`, `/api/site`, `/api/system/*`, etc. with the exact response shapes (types from packages/shared or api-client).
3. Relay performance metrics: what does the relay server (apps/gateway/src/relay/*) already track or could cheaply expose — per-tenant member count, online members, active streams, bytes in/out, frames/s, per-member RTT / last-seen, reconnect counts, sealed pack size/age, uptime, process memory/CPU (Bun `process.memoryUsage()`, `process.cpuUsage()`, `os.loadavg()`), event-loop lag, open sockets. Check what counters exist already (`relay-stream-router`, `relay-server`, tenant registry, mux stats in packages/shared/src/link/mux.ts, any `stats()` methods), what `/api/relay/*` or `/api/mesh/relay/*` endpoints exist and what they return, and whether there is any existing metrics/health route (`/healthz`, `/ready`, `/metrics`). Propose a concrete `GET /api/relay/metrics` (or extension of `/api/mesh/relay/status`) response shape that the frontend can poll every few seconds, plus an optional short in-memory ring buffer (e.g. last 60 samples) for sparklines. Also note what the *node side* knows about its relay link (uplink RTT, reconnects, bytes) for nodes that are not relays.
4. Check existing UI primitives in `packages/ui` (cards, stat/metric components, badges, sparkline/chart components, disclosure/accordion, tabs, section headers) and the design tokens/theme in `packages/theme`, so the redesign reuses them. Note the existing tests for the settings mesh components (file paths, counts) and the i18n workflow (`packages/shared/src/i18n/locales/*.json` → `bun run build:i18n`).
5. Also inventory the OTHER tabs of 多节点互联 briefly (names + purpose) so the redesign can move content to the right tab instead of deleting it.

Report everything as a structured document; it will be handed to the implementing agents verbatim.
