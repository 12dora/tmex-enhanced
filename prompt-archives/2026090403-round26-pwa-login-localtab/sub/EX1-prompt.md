# EX1 — login username default, i18n default language, PWA initial focus

Three frontend bugs observed on the production site https://tmexhub-sh.jiefakj.com (a node running roles `relay,node`, version 1.1.27; the user opens it as an installed PWA on iOS/macOS and also as a normal web page). Find the root cause of each and propose a concrete fix.

## Bug 1 — login form username is prefilled with a UUID-looking string
When opening the login page, the username field is prefilled with a string that looks like a UUID (32 hex / 8-4-4-4-12). The user says there must be NO default value at all. Find: which login page/component renders the username input (apps/fe, probably under auth / login routes, and `packages/ui` or `packages/panels` if relevant), where its initial value comes from (localStorage? a `users` list from `/api/auth/...`? mesh identity name? node id? site settings? a "remembered username" feature? passkey autofill hint?). Note the site is in relay mode: the mesh identity/user records may have been created by `tmex relay join` with a generated id. Distinguish between the local-login form (`/login`), the mesh login, and any "select account" UI. Also check whether the backend returns something like `defaultUsername` / `usernameHint` / `users[0].username` and where it's produced (apps/gateway auth routes, setup routes). Report the exact chain and the minimal fix (no default; keep browser autofill working).

## Bug 2 — UI language defaults to English instead of following the system/browser language
On first open (PWA and web), the UI shows English even though the device language is Simplified Chinese; only after opening Settings (设置) does it switch to Chinese. Find the i18n bootstrap: `packages/shared/src/i18n/*`, apps/fe i18n init, the settings store (`packages/stores`), any `language` preference persisted (localStorage key, server-side user preference `/api/settings` or `/api/site`), and the order of initialization (does the app render before the preference/`navigator.language` is applied? does the Settings page mount something that triggers `changeLanguage`? Is there a `resolveInitialLanguage()` that only runs in the settings page?). Also check the PWA manifest / service worker for a cached html `lang` attribute. Explain why visiting Settings fixes it and what the correct bootstrap should be (follow the saved preference if any, else `navigator.languages`, applied before first render, and consistent between web + PWA).

## Bug 3 — on first open of the PWA, focus lands on the "close sidebar" button (top-left, shown with a blue focus ring)
Find the sidebar component (apps/fe, `packages/ui`) and the "close sidebar"/collapse button; find any `autoFocus`, `.focus()` calls, `tabIndex`, focus-trap/`FocusScope`, or route-level focus management (e.g. a11y "focus first focusable on navigation") that would focus that button on initial mount, especially in standalone/PWA display mode (check `display-mode: standalone` media handling, iOS `viewport` policy code, `visibilitychange` handlers that call focus). Propose the fix (nothing should be focused on initial load; focus ring should only show for keyboard navigation — check `:focus-visible` usage).

Also report the relevant existing tests for these areas so the fixes can add/adjust tests.
