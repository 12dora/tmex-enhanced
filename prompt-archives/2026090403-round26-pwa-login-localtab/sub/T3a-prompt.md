## Production bug (root cause confirmed)
Entry site B (https://tmexhub-sh.jiefakj.com, roles relay,node) used to be a hub; after `tmex hub leave` + `tmex relay join` its node id changed. The user's PWA still holds per-node session cookies `tmex_s_<targetNodeId>` for 4 old nodes that were issued when B had its old node id. Sessions are bound to the entry node id (`viaNodeId`); the target now answers `401 {"error":"via_mismatch","code":"NODE_LOGIN_REQUIRED","nodeId":"…"}` (rewritten by the entry forwarder, `apps/gateway/src/mesh/forwarder.ts:805-842`). The frontend's `loggedIn` flag for a node only means "a cookie exists" (`apps/gateway/src/mesh/node-list-projection.ts:238-253`), so `useNodeLoginGate` (`apps/fe/src/auth/use-node-login.ts:76-105`, gate = `online && !loggedIn`) never re-logs-in, `fetchDevices` fails, and the devices panel shows the generic `device.loadFailed`. A new node (docker-node) works because it has no stale cookie.

The backend agent (T3b) is concurrently making the forwarder append a `Set-Cookie` that expires the stale `tmex_s_<target>` cookie on such 401s, and making `NODE_UNREACHABLE` 503 bodies carry a safe `reason` string. Your job is the frontend half:

1. `packages/api-client/src/client.ts` (`:83-96`): when a response is not ok, build a typed error that carries `status`, top-level `code` (e.g. `NODE_LOGIN_REQUIRED`, `NODE_UNREACHABLE`), `error` (e.g. `via_mismatch`), `nodeId`, and `reason` when present. Check what error class already exists in api-client (`ApiError`/`RelayApiError`/`readCodedError` in the codebase — reuse, don't invent a parallel one). `fetchDevices()` (`devices.ts:28-36`) must throw that typed error instead of a bare `Error(json.error)`.

Find the cleanest hook point: the react-query `onError` in `use-device-management-state.ts:41-46`, or a shared `handleNodeApiError(nodeId, err)` in apps/fe/src/node that the runtime scope exposes. Make sure this cannot loop (one re-login attempt per failure; if the re-login itself fails, surface the error).
