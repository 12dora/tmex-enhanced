# RV2 — Files sidebar visibility default + vertical-only DnD + static cache policy

Decisions already made: Files-sidebar per-device visibility now defaults to `stored ?? (runtimeNodeId === 'self' && hasRoots)` (matching the terminal sidebar); mounted node sections with zero visible roots render nothing; `SortableVerticalList` gets a local vertical-axis modifier; `ScrollArea` gains `axis="vertical"` that overrides Base UI's inline `overflow: scroll`; the packaged static server (`packages/app/src/runtime/serve-frontend.ts`) sends `immutable` for Vite hashed assets and `no-cache` + weak ETag / Last-Modified with 304 for the rest.

Review for: (1) users who had already explicitly enabled/disabled a device — is the stored value still honoured and keyed identically on the device card and in the sidebar (`${runtimeNodeId}:${deviceId}`, entry node = `self` on both sides)?; (2) empty-section suppression — loading flash, error state, node reorder (drag handles on sections that no longer render), keyboard/a11y; (3) the modifier — does it break keyboard sorting or the device-grid/device-folder contexts (they must be untouched)?; (4) `ScrollArea axis='vertical'` — does the inline style actually win against Base UI's viewport style, and are there other callers whose layout changes?; (5) cache policy — ETag correctness (mtime precision, size collisions), `If-Modified-Since` handling, `304` without body/Content-Length, hashed-asset regex false positives/negatives (e.g. `index-abc12345.js` vs `vendor.min-12345678.js` vs unhashed files inside `assets/`), path confinement unchanged; (6) the new e2e spec `apps/fe/tests/files-sidebar-drag.spec.ts` — will it be flaky (dnd-kit activation distance, pointer steps)?
