# RV1 — Auth: persisted session key (WebCrypto Ed25519 + IndexedDB), silent cross-node login, proxy-aware client IP

Context: mesh auth is described in `docs/hub/2026082700-hub-node-architecture.md` (§2 updated in this diff). Design decisions already made (do not re-litigate): the browser session key `sk_sess` may be persisted across documents only as a **non-extractable** WebCrypto `CryptoKey` in IndexedDB together with the root-signed delegation (18 h TTL); `kTotp`/TOTP codes are never persisted; TOTP-enabled password sessions are not persisted; `@noble` fallback stays memory-only. The login limiter and the bootstrap loopback decision use `resolveClientIp` (forwarded headers only when `TMEX_TRUST_PROXY`; `CF-Connecting-IP` presence always means non-loopback).

Review for: (1) any path where private key bytes could reach JS or disk; (2) restore/adopt/clear races (generation guard, queue ordering, logout deleting the record, expired records); (3) `ensureNodeLogin` awaiting restore — any caller that still relies on the sync `hasSessionKey()` and would now misbehave (grep the fe tree); (4) `establishSessionFromSeed` became async — all callers updated?; (5) the Devices page gate: could it fan out logins to many nodes repeatedly or loop on failure?; (6) gateway: client-IP parsing (IPv6 forms, spoofing when trustProxy=false, peer-forwarded requests via mesh — is `getMeshRequestContext(req).trustProxy` set correctly for `via !== self`?), loopback rule regressions for real local callers (CLI/onboarding on 127.0.0.1, IPv6 `::1`, `::ffff:127.0.0.1`); (7) the new integration tests actually assert the isolation properties they claim.
