A code review found these defects; fix all four with regression tests:

1. **Blocker — sized `TMUX_SELECT` bypasses arbitration.** `applyTmuxSelection` (tmux-command-handlers.ts ~136) calls `resizePane`/`selectPaneWithSize` directly with the selecting client's cols/rows, so a follower switching panes resizes the shared window to its own size, and the subsequent claim sees the owner geometry in `lastAppliedViewport` and does nothing. Fix: a sized select must go through the same claim path — record the claim for that session (visible, given geometry, new paneId) and only apply the size if that session is the current winner for the pane's window; otherwise select without size (and re-apply the winner's geometry if tmux drifted). Test: two sessions, large owner + small follower; follower selects another pane with its size → tmux stays at owner geometry; owner selects → applied.
2. **Major — `lastAppliedViewport` suppresses a legitimate re-apply.** With one client, after a tmux-side change (layout/pane resize from tmux itself), repeating the same `terminal-sync-size` is now suppressed because the cache still equals the requested geometry, whereas the old handler compared the live snapshot. Fix: decide "needs apply" by comparing the winner geometry with the **live snapshot window geometry** (fall back to the cache only when the snapshot is unavailable), or invalidate the cache whenever a snapshot reports a different geometry. Test: single client sync → tmux resized out-of-band (simulate snapshot change) → same sync again → applied.
3. **Major — pane switch inside the same window yields no policy for the new pane.** "First claim" is tracked per window key; when the winner/geometry are unchanged the new `paneId` never receives `TERM_VIEWPORT_POLICY`, so the client's store (keyed by pane) defaults that pane to owner. Fix: a claim whose `paneId` differs from the session's previous claim on that window must trigger an immediate policy message to that session for the new pane. Test: follower claims `%0` then `%1` in the same window → receives policy for `%1` with `owner:false`.
4. **Major — claims keyed by a stale window after a pane moves windows / window closes.** Fix pragmatically: when resolving the winner for a window, re-resolve each claim's `paneId` against the current snapshot; drop claims whose pane no longer exists or now belongs to another window (recompute both windows); remove `lastAppliedViewport` entries for windows that no longer exist. Test: claim on `@1`, snapshot moves the pane to `@2` → no resize of `@2` is issued from the `@1` claim; state for `@1` cleaned.

5. **Minor (separate file, `apps/gateway/src/mesh/integration/mesh.integration.test.ts` ~969 and ~1007)** — two recently added isolation tests pass through unrelated rejection paths: the "login signed for A rejected by B" case submits A's challenge to B so B rejects with `CHALLENGE_CONSUMED` before target binding; the "A's SID rejected by B" case uses a SID that only exists in A's DB so B rejects it as unknown before checking `viaNodeId`. Rewrite them so they exercise the named bindings: build the forged login from a **B-issued** challenge but keep A's `target`/`target_pk` and assert `TARGET_MISMATCH`; for session isolation, issue a SID in B bound to `self` (or another entry) and present that same SID through A's forwarder path, asserting rejection on `viaNodeId`.

Keep the existing behaviour for the single-client path otherwise identical; keep functions under the complexity gate (`bun scripts/complexity/gate.ts` must show no gateway violations). Update the doc's edge-case section.
