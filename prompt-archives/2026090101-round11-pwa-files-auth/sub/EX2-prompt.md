# EX2 — Multi-client terminal viewport coupling (phone vs desktop)

User report: when the same tmux pane is open in the iOS PWA and on the desktop browser at the same time, the desktop view "follows" the phone: the pane shrinks to phone proportions, and scrolling on the phone scrolls the desktop too. Desired: each client keeps its own **size** and its own **scroll position**, while **input remains shared** (typing on the phone must still appear on the desktop, and vice versa — it is the same pane/PTY).

Investigate and report exactly how the current pipeline works, then design options:

1. **Attachment model**: how does the gateway attach to tmux — control mode client (`tmux -C`), `pipe-pane`, `capture-pane`, one tmux client per browser or one shared? See `apps/gateway/src/tmux`, `apps/gateway/src/tmux-client`, `apps/gateway/src/ws`, `apps/gateway/src/control`. What is the tmux `window-size` / `aggressive-resize` setting the gateway relies on, and does it call `resize-window`, `resize-pane`, `refresh-client -C`, or `-x/-y` on attach?
2. **Resize path**: trace a browser resize from `packages/terminal-ui` / `packages/ghostty-terminal` (fit/observer) → WS message (`packages/shared/src/ws-borsh`, RESIZE or similar) → gateway handler → tmux command. Is the pane/window size a single shared value (last client wins / smallest wins)? Is there any per-client notion of viewport at all? What happens when two clients disagree?
3. **Scroll path**: is scrollback rendered client-side (ghostty VT emulator holding its own scrollback fed by the raw byte stream) or server-side (tmux copy-mode / `capture-pane -S`)? Where does "scrolling on the phone scrolls the desktop" come from — tmux copy-mode being entered on the shared pane, mouse-wheel escape sequences forwarded to the PTY (`mobile-mouse-reporting`, wheel-to-arrow translation), or a client-side scroll position being broadcast? Read `packages/terminal-ui/src` scroll/wheel handling, `apps/fe` mobile terminal interactions, and the gateway mouse/scroll handling.
4. **What is per-client vs shared today**: theme, font size, selection, alt-screen, mouse-mode state, `TERM_HISTORY` restore (`writeRestoredHistory`), keep-alive stack.
5. **Design options** to decouple size and scroll per client while keeping the PTY/input shared. Consider at least:
   - (a) tmux-level: one tmux client per browser client with `window-size latest`/per-client size and independent copy-mode per client (tmux already supports independent scroll per attached client in copy-mode? verify against tmux semantics: copy-mode is per pane, not per client — state precisely what tmux allows);
   - (b) gateway-level "virtual viewport": PTY sized to the largest/desktop client, phone client renders the same byte stream into its own ghostty instance with its own cols/rows and handles overflow by horizontal scroll or reflow; identify what breaks (TUI apps assume the PTY size);
   - (c) policy tweaks only: e.g. "size follows the most recently *focused/interacting* client, not the most recently connected/resized one", ignore resize from a client that is hidden/backgrounded, never propagate a *smaller* size from a mobile client unless it is the only client; scroll: keep scrollback client-side and stop forwarding wheel-to-copy-mode when another client is attached.
   For each option: affected files, complexity (S/M/L), risk to existing e2e specs (`apps/fe/tests/e2e/*` — mention spec names that would need changes), and whether it satisfies "input stays shared".
6. Recommend one option (or a combination) that a team can implement in a day and that gives the user the requested behaviour, and list the exact functions to change.

Note: `docs/terminal`, `docs/ws-protocol`, `docs/performance` and `docs/known-issues.md` may document intended behaviour — cite them but verify against code.
