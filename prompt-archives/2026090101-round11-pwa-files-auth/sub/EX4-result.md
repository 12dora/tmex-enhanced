# EX4 — Public-Internet Password Login Security Review

## Bottom line

In the normal packaged runtime, authentication is materially stronger than conventional password auth: the browser derives an Ed25519 root key from the password using Argon2id, then signs a challenge. The gateway never receives or compares the password itself. Sessions are opaque, random, server-side records, and WebSocket authentication uses the same cookie session rather than a URL bearer token. Evidence: `apps/fe/src/auth/session-login.ts:57-105`, `packages/shared/src/auth/root-key.ts:5-47`, `apps/gateway/src/mesh/auth-routes.ts:304-322`, `apps/gateway/src/auth/node-session-store.ts:46-119`.

The realistic concerns are deployment-related:

1. First-time standalone bootstrap can become remotely reachable through a local tunnel if the tunnel is not protected by Cloudflare Access.
2. The bare `@tmex/gateway` entrypoint bypasses the assembled application authentication layer if exposed directly.
3. Plain HTTP makes session theft trivial.
4. The rate limiter does not understand Cloudflare client IPs and may collapse all tunnel users into one bucket.
5. The eight-character minimum makes offline password guessing more relevant, although online guessing is strongly throttled.

## Brute-force realism

The online limit is approximately 10 failed attempts per minute per effective IP bucket and 10 per minute per UID bucket, or about 0.167 attempts/second per bucket (`apps/gateway/src/mesh/auth-routes.ts:800-822`). There is no server-side Argon2 computation per attempt: Argon2id runs in the browser before the signed login request is sent (`apps/fe/src/auth/session-login.ts:91-105`). Therefore the online rate is controlled by the limiter, not the 64 MiB Argon2 cost.

A distributed attacker can use many source IPs, but the UID bucket still caps guesses against one known account. Through a local Cloudflare Tunnel, the IP bucket may collapse all users together because the application records the Bun socket address rather than `CF-Connecting-IP`; this is more likely to create denial-of-service friction than to improve password protection (`packages/app/src/runtime/assemble.ts:141-152`, `apps/gateway/src/mesh/session-middleware.ts:228-245`).

The Argon2id parameters—64 MiB memory, three iterations, one lane, 32-byte output, 16-byte salt—are reasonable for client-side derivation (`packages/shared/src/auth/root-key.ts:5-47`). An exact offline guesses-per-second number cannot be established from source alone and requires hardware benchmarking. The practical control is a random password or passkey, not additional password complexity rules.

## Recommended minimal set

1. Make first-time bootstrap unavailable through an untrusted tunnel. Bootstrap locally before exposure, require Cloudflare Access, or implement trusted-proxy-aware client-IP validation.
2. Make the login limiter proxy-aware only when the proxy is explicitly trusted; preserve direct-connection behavior otherwise.
3. Ensure public deployments use the assembled runtime and HTTPS, with `TMEX_TRUST_PROXY=true` behind an HTTPS tunnel.
4. Document a password-manager-generated 16+ character password or passkey as the expected setup.

## Deliberately do not recommend

- Migrating to server-side bcrypt/Argon2 password hashes; the current challenge-signing design avoids sending the password and is not the main weakness.
- Global lockouts, aggressive backoff, or complex password rules; these add account-denial and usability costs while the UID limiter already exists.
- JWTs, `localStorage` bearer tokens, or WebSocket `?token=` URLs; the current cookie/session design is safer.
- App-wide HSTS without considering HTTP localhost and self-signed deployments; configure it at a controlled public edge if desired.
- Adding a password layer to peer authentication; node certificates already provide the independent trust boundary.
- Tightening passkey hostname binding; strict origin binding is the correct behavior.

## EX5 cross-node login interaction

A session minted through node A cannot be replayed directly on node B: the session record contains `viaNodeId`, and verification rejects a mismatch (`apps/gateway/src/auth/node-session-store.ts:12-24,79-98`). Cookies are also named per node, and remote forwarding reads the target node’s cookie (`apps/gateway/src/auth/cookies.ts:20-22`, `apps/gateway/src/mesh/forwarder.ts:254-263,619-637`).

The existing cross-node flow instead performs a fresh target-bound login using the in-memory root/session key, a fresh challenge, and the target node public key (`apps/fe/src/auth/session-login.ts:325-369`, `packages/shared/src/auth/login.ts:23-74`). EX5 should preserve this model and mint a separate B-bound session. Copying A’s `sid` to B would correctly fail today; weakening the `viaNodeId` check would create a serious cross-node replay vulnerability.
