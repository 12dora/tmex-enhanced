# EX5 — Automatic cross-node sign-in using the local node's credentials (mesh SSO)

User report: on a phone (iOS PWA) that has just signed in to its "home" node, every other mesh node still asks for username + password once each. Desired: when the user opens another node, the app should first try to authenticate automatically using the credentials/session it already holds on the home node, and only fall back to the manual login form if that fails — **without breaking the security boundary between nodes**.

Map the current system, then design the feature:

1. **Current per-node auth model**: how the SPA talks to a remote node — via the home gateway proxying (`peer-link`, `/api/mesh/nodes/:id/...` forwarding), or by the browser connecting directly to the remote node's URL / relayed WS? See `apps/gateway/src/mesh`, `apps/gateway/src/hub`, `packages/shared/src/uplink`, `apps/fe/src/node`, `apps/fe/src/auth`, `packages/api-client`, `apps/fe/tests/helpers/mesh.ts` (`signInToNodeFromDevicesPage`), `docs/hub`. Where is the per-node session kept in the client (memory only? — the e2e helper notes the session key is lost on reload), what is the login request to a remote node (endpoint, payload, transport), and what does the remote node verify?
2. **Identity & trust that already exists between nodes**: node certificates (`node_certs`, `peer_cache`, key-log seq), hub-signed node list, peer-link mutual auth, mesh "user" concept — is there a mesh-wide user identity, or does each node have its own independent user table + password? Are passwords/accounts ever synchronised across nodes? Is there any existing token-exchange, "trusted node" or "hub session" concept that could be reused?
3. **Why the user is asked per node today** — the precise code path that yields the login prompt on first visit to node B, and why the home session cannot be reused (different origin? different user DB? no token forwarding?).
4. **Design options** (analyse each against the existing trust model; be specific about what is signed by whom, TTL, audience, replay, revocation, and what a compromised node A could do to node B):
   - (a) **Credential replay**: client caches the username/password it typed for the home node (in memory / IndexedDB / passkey-derived) and tries the same on node B. Simple, but discuss storage risk on the device and the fact that it only works when accounts are identical.
   - (b) **Node-signed assertion**: home node A mints a short-lived assertion `{sub: user, aud: nodeB, iat, exp, nonce}` signed with A's node private key; B verifies against A's cert from the hub-signed node list, then maps `sub` to a local account (same username must exist? or any authenticated user of a trusted mesh node is accepted?), and issues its own session. Discuss: does mesh membership already imply "A's users are trusted on B"? Is there an existing per-node "trust level"/role model (`packages/shared/src/roles.ts`)?
   - (c) **Hub-mediated**: hub issues the assertion instead of A (hub is already the root of trust for node lists).
   - (d) **Proxy everything through the home node** so the browser never authenticates to B (peer-link already forwards `/api/system/upgrade` — could it forward the whole API/WS?). Note bandwidth/latency implications for terminals.
5. **Security boundary analysis**: today, does compromising node A's password give access to node B? Does the proposed design change that answer? Identify the invariant to preserve (e.g. "a node only accepts an assertion for a user that exists locally with the same username, and only from nodes in the current hub-signed node list", or "opt-in per node: 'accept mesh sign-in from trusted nodes' setting"). Recommend whether an opt-in toggle is required or whether mesh membership alone is sufficient consent, and whether the fallback to manual login should be silent or show a notice.
6. **Recommendation**: pick one option, list the exact endpoints/messages to add (gateway routes, borsh/JSON schemas, DB tables/columns, `packages/api-client` methods, FE flow in the node switch / devices page), the client-side fallback logic (try auto → on 401/403 show the existing form pre-filled with username), and the tests (gateway unit tests with two in-process nodes; e2e `--project mesh` spec). Estimate size (S/M/L) split into backend vs frontend so it can be assigned to two agents in parallel, and state which shared contract (`packages/shared/src/contracts` or `uplink`) both must agree on first.

Coordinate with EX4's concern: a token minted for node A must not be replayable on node B unless that is the intended mechanism, and if so it must be audience-bound and short-lived.
