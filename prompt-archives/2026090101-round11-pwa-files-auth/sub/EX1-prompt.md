# EX1 — PWA load & steady-state transfer audit

User report: the iOS PWA (installed web app pointing at the gateway) has become slow, both on first open and during later use. Suspicion: unnecessary data is being transferred, or data keeps flowing for things that are not currently displayed.

Investigate and report:

1. **Boot sequence of the SPA** (`apps/fe/src/main.tsx`, page wrappers, `packages/stores`, `packages/api-client`, `packages/ws-client`): list every HTTP request and every WS subscription/message the client issues before the first terminal is interactive, in order, with the code location that triggers it. Identify which are blocking (awaited before render) and which are fire-and-forget. Flag anything that is large, duplicated, serialised when it could be parallel, or not needed for the first screen (e.g. full mesh node list with endpoints, file roots, device folders, settings, LLM providers, i18n bundles, fonts, WASM for ghostty).
2. **Service worker / PWA caching** (`apps/fe` vite PWA config, `public/`, manifest, SW registration): what is precached, what is network-first, whether the app shell and the ghostty WASM/fonts are cached, whether a version bump invalidates everything, and whether there is anything that forces a full re-download on each launch.
3. **Steady-state traffic**: what keeps flowing while the app is open — polling timers (`setInterval`, react-query refetch intervals, `refetchOnWindowFocus`), WS broadcast subscriptions (device status, mesh node presence, file watchers, agent sessions, notifications). For each: does it continue when (a) the panel that displays it is closed/hidden, (b) the page is in the background (`document.visibilityState === 'hidden'`), (c) the terminal pane is not visible (keep-alive stack `KeepAliveTerminalStack`, background panes in split layouts, other windows/sessions). Pay particular attention to whether the gateway keeps streaming pane output (`pipe-pane` / control-mode `%output`) for panes the client is not looking at, and whether `TERM_HISTORY`/scrollback payloads are sent for panes never shown.
4. **Gateway side** (`apps/gateway/src/ws`, `apps/gateway/src/tmux`, `apps/gateway/src/mesh`): per-client subscription model — is output fan-out per pane per client, or broadcast to all clients? Are there per-message overheads (e.g. re-sending full window/layout snapshots on every change, JSON-encoding large structures, sending mesh node lists with certificates)? Look at the borsh protocol in `packages/shared/src/ws-borsh`.
5. **Recent regressions**: `git log --since=2026-08-25 --stat` on `apps/fe`, `packages/stores`, `packages/ws-client`, `apps/gateway/src/ws` — identify commits (rounds 5–10: remote agent, files multi-node, relay badge, keep-alive stack, node upgrade, onboarding panel) that added new boot-time or steady-state traffic. Where possible, estimate the byte size of new payloads.

Deliverable: a ranked list (highest expected impact first) of concrete waste items, each with evidence (`path:line`), estimated impact (bytes / requests / CPU) on a mobile client, and a proposed fix with file/function names. Separate "safe quick wins" from "needs design". Also state explicitly which things you checked and found fine.
