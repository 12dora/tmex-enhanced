# EX6 — How a terminal surface is displayed when emulator geometry ≠ container geometry

Follow-up to an earlier exploration (EX2) which established: one shared tmux PTY per pane; every browser's `terminal-resize` calls `resize-window`, so the last client wins; each browser has its own Ghostty (WASM) emulator; `usePaneSizeSync` (`packages/panels/src/device-console/use-pane-size-sync.ts:91-129`), `writeRestoredHistory`/`convergeSnapshotSize` (`packages/terminal-ui/src/components/terminal-snapshot.ts:115-190`) and `useTerminalBootSurface` (`packages/terminal-ui/src/components/hooks/useTerminalBootSurface.ts:210-225`) force the local emulator to the tmux geometry; keep-alive hidden instances use `sizingMode='local'` (`packages/panels/src/device-console/terminal-stage.tsx:306`).

We plan: the shared PTY follows the **largest visible client**; a smaller client (phone) must then display a pane whose emulator geometry (e.g. 200×50) is larger than what fits its container (e.g. 45×30 at its font size). Answer precisely, with `path:line`:

1. **Rendering pipeline**: how does `packages/ghostty-terminal` draw — canvas 2D / WebGL, one canvas per terminal, DPR handling, `terminal-render-target.ts`, `terminal-render-coordinator.ts`. When `terminal.resize(cols, rows)` is called with a geometry larger than the container, what happens visually today: is the canvas element resized to `cols*cellW × rows*cellH` (overflowing the container, clipped by `overflow:hidden`?), or is the container's CSS size fixed and the canvas drawn partially? Where is the container/canvas CSS (`Terminal.tsx`, `terminal-render-target.ts`, `packages/terminal-ui/src/**/*.css`, `apps/fe/src/app.css`)?
2. **Split windows**: `SplitTerminalArea` renders multiple panes from a tmux layout (`packages/shared/src/tmux-layout.ts`) — how is each pane's emulator geometry reconciled with its grid cell? Is there any CSS `transform: scale()` or font-size adaptation anywhere so a pane "fits"? Is there any existing "fit to width" / auto font-size logic on mobile (`packages/stores/src/ui.ts` font size, `useTerminalBootSurface`)?
3. **`sizingMode`** in `Terminal.tsx` (`'report' | 'local'`): exact semantics of each, who calls `report()` vs `sync()` in `terminal-resize-reporter.ts`, and what `terminal-sync-size` means on the gateway (`apps/gateway/src/ws/tmux-command-handlers.ts`) vs `terminal-resize`.
4. **Feasibility of "render at PTY geometry, pan locally"** for a small client: list the concrete changes to (a) stop the small client from sending `terminal-resize` when another larger client is visible (needs gateway to tell clients the current policy winner — identify the existing snapshot/metadata message that carries pane cols/rows to clients, e.g. tmux snapshot / `pane` rows in `packages/shared/src/ws-borsh`, and whether it could carry a `sizeOwner`/`viewportPolicy` hint), (b) size the canvas to the emulator geometry and make the wrapper horizontally+vertically scrollable/pannable on touch (which element gets `overflow:auto`, interaction with the existing touch gesture machine `packages/terminal-ui/src/components/touch/*` which currently maps drags to scrollLines/wheel — how to distinguish pan vs scrollback), and (c) keep `usePaneSizeSync` history rebuild logic correct. Identify the e2e specs asserting the current behaviour (`ws-borsh-resize.spec.ts`, `terminal-render-regressions.spec.ts` bug4, `ws-borsh-theme-resize.spec.ts`, `mobile-*`) and which assertions would change.
5. Alternative to (4b): CSS `transform: scale(k)` on the canvas wrapper so the whole PTY-sized surface fits the container width (zoomed-out view) with the existing pinch/zoom? Say whether Ghostty's hit-testing (mouse/touch → cell coordinates in `terminal-input-bridge.ts`) would break and where it converts pixels to cells.
