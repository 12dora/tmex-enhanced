## Task F1 — Node management must not flash "无法连接到 Hub" before the first Hub probe finishes

Scope (only these paths): `apps/fe/src/pages/settings/nodes/uplink/hub-uplink-panel.tsx` (+ its `.test.tsx`), `apps/fe/src/pages/settings/nodes/uplink/local-uplink-tabs.tsx` (+ test) if you need to pass `loading` through, `apps/fe/src/node/mesh-nodes.ts` (+ `mesh-nodes.test.ts`) and `apps/fe/src/node/hub-load-coordinator.ts` (+ test) ONLY if you need a tri-state, and i18n keys under `nodes.*` in `packages/shared/src/i18n/locales/zh_CN.json` / `en.json` (or whatever the en file is named — check). Result file: `/Users/konata/code/tmex-r25/prompt-archives/2026090402-round25-relay-live-bots/sub/F1-result.md`.

Findings from the code exploration (verify them yourself first):
- `useHubNode` (`apps/fe/src/node/mesh-nodes.ts:715-778`) exposes `online: hubNodes !== null`, `loading`, `failure`. Initial render has `hubNodes=null, loading=false, failure=null` → `online=false`.
- `HubUplinkNotices` (`apps/fe/src/pages/settings/nodes/uplink/hub-uplink-panel.tsx:213-240`) renders the `nodes.hubOffline` banner whenever `hubOnline === false`, with no check of `loading` or `hubFailure === null`. So on every entry into Settings → Nodes the red "无法连接到 Hub，节点管理暂不可用。" banner shows until the first `GET /n/<hub>/api/hub/nodes` (which may first 401, silently login, retry) succeeds. The sidebar, which uses `useMeshNodes`, is fine — the user finds this misleading.
- `hub-load-coordinator.ts:118` drives `loading`/`failure`; `nodes-management.tsx:56` computes `writable = hub.online && !hubs.writesBlocked`.

Required behavior:
1. The offline banner must appear only when a probe has actually concluded with a failure (`hubFailure !== null`), never in the initial/loading/reset state. Keep `nodes.hubLoginRejected` for auth failures and keep the standby notice precedence.
2. While the first probe (including the 401 → silent login → retry sequence) is in flight, show a subtle, non-alarming inline status (muted text, e.g. 「正在连接 Hub…」/ "Connecting to Hub…", new i18n key `nodes.hubConnecting`) in place of the banner, so the page does not look broken and does not look "offline". Do not show it on subsequent background refreshes once rows have loaded (i.e. only when `hubNodes === null && loading`).
3. Do NOT change the semantics of `online` (it means "last hub list succeeded"); do not treat loading as online; `writable` stays false until loaded.
4. If a probe fails and then a later refresh succeeds, the banner must disappear (already true — keep a test for it). If a probe succeeds and a later refresh fails, decide: keep showing the last rows but show the banner (current behaviour: failure clears rows — check `sink.failed` in coordinator; keep current behaviour unless trivially better).
5. Tests: add cases in `hub-uplink-panel.test.tsx` (initial state → no banner; loading → connecting text; failure unreachable → offline banner; failure auth → login rejected; standby precedence). Export `HubUplinkNotices` if needed for testing. Run `cd apps/fe && bun test src/pages/settings/nodes src/node` and `bunx tsc --noEmit -p .` (baseline 0 errors), `bunx biome check` on your files.
6. i18n: add `nodes.hubConnecting` to both locale JSONs (zh-CN + en). Do NOT run `bun run build:i18n` (the commander does it); if TypeScript complains about the missing key in the generated types, note it in the result and the commander will regenerate.
