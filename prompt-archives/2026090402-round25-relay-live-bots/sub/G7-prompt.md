## Task G7 — `readmit-node` key-log record: re-affirm existing members under the current root so a rotated-root account can migrate to a relay

Result file: `/Users/konata/code/tmex-r25/prompt-archives/2026090402-round25-relay-live-bots/sub/G7-result.md`. Version is being bumped to 1.1.26 by the commander (do not edit package.json).

### The production failure (verified today)
Account root epoch is 4 (three `rotate-root-keep`), but every `admit-node` in the key log was signed at root epoch 1 by the epoch-1 root key. When the entry node enrolled to a relay (`POST /api/mesh/relay/enroll` → tenant created with the CURRENT root pk / `root_epoch: 4`) and applied `set-relays`, its `relay.auth` was refused with `member-epoch_mismatch`: `apps/gateway/src/relay/relay-member.ts:115` requires `record.root_epoch === tenant.root_epoch`, and even without that check the old records are signed by a root pk the relay never knew. Historical members therefore can never attach; the whole mesh is stranded. `apps/gateway/src/mesh/relay-uplink-auth.ts:44` presents the record at `node_certs.admit_record_seq` as the member proof (`selfAdmitMemberProof`), and `relay-key-log-sync.ts` uploads history with sidecars built by `relayMemberFromRecord()`.

### Design to implement
1. **New record type `readmit-node`** in `packages/shared/src/auth/key-log.ts` (+ `hub-authorization`/`KEYLOG_RECORD_COMPAT`: `minVersion: '1.1.26'`, `allowForce: false`; export `MIN_READMIT_NODE_RECORD_VERSION`). Payload = exactly the `admit-node` payload (`authorization_bytes`, `authorization_sig`, `certificate_bytes`, `cert_sig`; reuse `encodeAdmitNodePayload`/`decodeAdmitNodePayload`). Signers: `root` or `passkey` (same as admit-node). `applyReadmitNode`: verify exactly like `applyAdmitNode` (authorization sig against the CURRENT `state.rootPublicKey` or passkey assertion, cert sig, enroll_pk match, uid match) BUT require that `state.nodeCerts` already has an UNREVOKED cert for that node id whose `certificateBytes` are byte-identical; then replace the stored `authorizationBytes`/`authorizationSig` (certificate unchanged). Errors: `unknown_node` (no cert), `node_revoked`, `certificate_mismatch`. Add the type to the DB CHECK constraint of `user_key_log.type` (new migration `0045_readmit_node_keylog.sql`, follow how 0042 added `rename-node`, register in `managed-migrations.ts` + journal) and to `ALL_KEYLOG_TYPES`/validators wherever `rename-node` was added in round 24 (grep `rename-node` across `packages/shared`, `apps/gateway`, `packages/app` and mirror every registration point, including the relay codec limits if any, `relay-records`/`hub-authorization` node-side record lists, `auth-key-log-routes.ts` planning table — a `readmit-node` in ANY mode is local-first + publish like other records; in hub mode it must go through the writer like `admit-node`).
2. **Gateway apply effects**: wherever applying `admit-node` upserts `node_certs` with `admit_record_seq` (search `admitRecordSeq` in `apps/gateway/src/auth/user-store.ts`, `mesh/key-log-*`, `hub/node-persistence.ts`, `hub/uplink-server.ts`), a `readmit-node` must update the existing cert row's `admit_record_seq` (and authorization bytes/sig) to the readmit record's seq so `selfAdmitMemberProof` presents the NEW record. Hub `nodes` table: no status change; keep name.
3. **Relay side**: `relayMemberFromRecord()` (`mesh/relay-key-log-sync.ts`) maps `readmit-node` → `op: 'admit'`; `verifyRelayMember` (`relay/relay-member.ts`) accepts record type `readmit-node` for `op admit` (type check), same epoch + signature rules (the readmit record is signed at the current epoch by the current root, so it passes).
