### Background (from a code audit — verify yourself)
Telegram (`apps/gateway/src/telegram/service.ts`, GramIO long polling) only understands the exact string `/start` (binding). Weixin (`apps/gateway/src/weixin/service.ts` + `weixin/ilink/*`, iLink long polling; `toInbound()` already yields `{fromUserId, contextToken, text}`) parses no commands at all; `handleInbound()` only upserts the user. Both are notification sinks (`apps/gateway/src/events/channels/{telegram,weixin}.ts`, shared raw-view builders in `notification-format.ts`). Neither knows about mesh nodes (`/api/mesh/nodes`, `peer_cache`, `node_identity`), hubs or relays; bot config and chat authorization are node-local tables (`telegram_bots`, `telegram_bot_chats`, `weixin_accounts`, `weixin_users`, no `nodeId`). Agent confirmations exist over HTTP (`POST /api/agent/confirmations/:id/decide`, see `apps/gateway/src/api/agent-confirmation-routes.ts`) but no chat command can decide them. Neither channel chunks long messages (Telegram limit 4096 chars; iLink single text item). Telegram authorization stores only `chat.id` (whole group), not `from.id`.

### Goal
One platform-agnostic command layer so Telegram, Weixin, and a future DingTalk bot share the same command set, parsing, node targeting, rendering and tests. A new platform must only implement an adapter.

### Design to implement
1. `packages/shared/src/messaging/`:
   - `command-types.ts`: `CommandSpec { name; aliases; args: ArgSpec[]; descriptionKey; requires: 'read' | 'execute' | 'approve' }`, `CommandInvocation { command; args; rawText; actor: { platform: 'telegram'|'weixin'|'dingtalk'; accountId; conversationId; userId: string|null }; nodeTarget?: string }`, `CommandResult { text?: string; sections?: {title?: string; lines: string[]}[]; actions?: {label: string; command: string}[]; error?: {code: string; params?} }` — results are structured, never platform markup.
   - `command-parser.ts`: tokenizer supporting a leading `/` (optional), `/cmd@botname` suffix (Telegram groups), quoted args, `--node <name|id>` or a leading `@<node>` token for node targeting, `--` separator before a free-form command tail (for `run`). Pure, fully unit-tested.
   - `node-target.ts`: `resolveNodeTarget(input, { localNodeId, localName, nodes: {id, name, online}[] })` → exact id, then case-insensitive name, then unique prefix; ambiguity/unknown/offline return typed errors. `self`/empty → local.
   - `chunk.ts`: `chunkText(text, maxChars)` that splits on line boundaries first, then hard-splits, never splitting a UTF-16 surrogate pair.
2. `apps/gateway/src/messaging/`:
   - `registry.ts`: `createCommandRegistry()` with `register(spec)`, `find(nameOrAlias)`, `list()`.
   - `adapter.ts`: `MessagingAdapter { platform; limits: { maxTextChars; supportsActions }; render(result): string[] (already chunked); parseInbound(...)?: not needed — parsing is shared; formatting is `plain` for Weixin and Telegram-HTML for Telegram (escape!) }`.
   - `executor.ts`: `dispatchCommand(invocation, ctx)`: authorize actor → resolve node target → if the target is not the local node, return a structured error `messaging.error.remoteNodeUnsupported` explaining that commands run on the node that owns the bot (put the design hook for a future remote executor in the interface, but do NOT implement cross-node execution — there is no server-side credential for remote nodes). Handlers get a `CommandContext` with local services.
   - `handlers/*.ts`, first command set (English keywords, stable; help text localized):
     - `help` — list commands with descriptions.
     - `status` — local node name (`node_identity.name` → site name fallback), version, roles (`TMEX_ROLES`), uplink kind (hub/relay/none) and whether the uplink is attached — find the right accessors (`apps/gateway/src/mesh/*`, `/api/local/status` implementation in packages/app is out of scope; use what gateway exposes; if the uplink state lives only in packages/app, expose a small registration hook in `apps/gateway/src/messaging/context.ts` that packages/app can set later and report `unknown` when unset — document it in the result).
     - `nodes` — mesh nodes from the same source `/api/mesh/nodes` uses (name, online, version, "current" marker). In standalone mode: say so.
     - `devices [--node]` — local devices (name, type, connection state).
     - `windows <device>` / `panes <device> [window]` — from the tmux tree source the HTTP API uses (`/api/tmux/tree` or the state snapshot; find the service function, do not spawn tmux yourself).
     - `tail <device> <pane> [lines=30]` — last N lines of a pane via the existing capture facility used by the gateway (find it; e.g. the tmux client `capture-pane` helper). Cap lines ≤ 200; output goes in a monospace block for Telegram.
     - `run <device> <pane> -- <text>` — send keys + Enter to a pane via the existing tmux input path (the same function the WS `TerminalInput` canonical handler uses). Requires `execute`.
     - `approve <confirmationId>` / `deny <confirmationId> [reason]` — decide a pending agent confirmation via the same service the HTTP route calls. Requires `approve`.
     - Device/pane references: accept device name (unique, case-insensitive) or id; pane accepts `%N` id or `window.pane` index like `1.0`; ambiguity → error listing candidates.
   - Per-bot permission: add a boolean column `allow_commands` (default 0) to `telegram_bots` and `weixin_accounts` (migration 0044), expose as `allowCommands` in the contracts, DB rows/mappers, and the create/update routes (validate boolean). `requires: 'read'` commands and `help` work whenever the chat/user is authorized AND `allowCommands` is true; `execute`/`approve` also need `allowCommands`. (Keep it one flag; the FE toggle comes later.) For Telegram, additionally record `from.id` as `user_id` on the chat row (new nullable column in the same migration) at `/start` time, and for commands in group chats only accept messages whose `from.id` equals the stored `user_id` (a group binding therefore belongs to the user who bound it). Keep `/start` binding behaviour byte-for-byte otherwise.
   - Telegram adapter: HTML rendering with escaping, code blocks for `tail`, chunk at 4000 chars; reply in the same chat. Weixin adapter: plain text, chunk at 2000 chars (check iLink limits in `weixin/ilink/client.ts`; if unknown use 2000), reply via `contextToken`. Unknown command → short hint to `help`. Unauthorized/pending chats: keep the existing silence (no reply) except `/start` binding.
   - Wire: in `TelegramService` the `bot.on('message')` handler: `/start` → existing binding; else → dispatch. In `WeixinService.handleInbound()`: after the existing upsert, if the user is authorized and text non-empty → dispatch and reply.
