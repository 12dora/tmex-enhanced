# EX2 — Gateway: per-pane upstream output subscription in tmux control mode

Question: the gateway attaches one tmux control-mode client per device and parses every `%output` for every pane, even panes no browser observes. For remote (SSH) devices this costs upstream bandwidth and gateway CPU. Design a per-pane upstream retention/subscription strategy.

Investigate and report:

1. Current control-mode pipeline: `apps/gateway/src/tmux-client/control-mode-subscription.ts`, `tmux-client/external/control-mode-lifecycle.ts`, the parser, and how `%output` reaches `legacy-feed-broadcaster.ts` and the canonical `pane-stream.ts`. Where is the "observed panes" set (ref-counted per client) and is it visible to the tmux-client layer?
2. tmux capabilities: verify against the tmux man page / source what control mode offers for flow control: `refresh-client -A pane:state` (`on`/`off`/`continue`/`pause`), `-f pause-after=N` / `-f no-output`, `%pause`/`%continue` notifications, `%extended-output`. Which tmux version introduced each (need ≥ 3.2 for `-A`; check what version the project assumes — search for version checks / `tmux -V` parsing in `apps/gateway/src/tmux-client/**`). Does `refresh-client -A pane:off` stop tmux from *sending* output for that pane in control mode, and what happens to the pane's own scrollback/history while off (it still accumulates in tmux, so `capture-pane`/history request on re-observe is enough to catch up)?
3. Other gateway consumers of pane output that are NOT browser clients: agent `run_command` / streaming screen readers (`apps/gateway/src/agent/**`, docs `docs/agent/2026061303-run-command-headless-ghostty.md`), watch rules (`apps/gateway/src/watch/**` or similar — anything matching pane output for notifications), headless ghostty emulators kept per pane, history caches, activity/bell detection. Each of these would break if upstream output is turned off for an unobserved pane. List them precisely with citations; this decides whether the item is feasible at all.
4. Reconnect correctness: what happens on control-mode reconnect (pane flags reset to `on`), pane creation (new panes default `on`), and client disconnect (must not leave a pane paused forever). Where would the "desired upstream set" be reconciled?
5. Options: (A) `refresh-client -A pane:off` for panes with zero observers AND no non-browser consumer, `on` + history catch-up on first observer; (B) `-f pause-after` flow control only (bounded backlog, tmux pauses itself under pressure; less saving but no correctness risk); (C) do nothing — quantify roughly what fraction of upstream bytes are for unobserved panes in a typical session (e.g. a busy build log in a background pane).
6. Recommend, estimate diff size, and list the integration test approach (the repo has `local-external-connection.integration.test.ts` using a `-L` temporary tmux socket — note the rule: never touch the default socket or a session named `tmex`).
