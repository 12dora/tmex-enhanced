## Blocker

- **Event-driven mesh refreshes can be swallowed by an existing request.** `runRefresh()` records the trigger and invokes `refresh()` unconditionally (`apps/fe/src/node/mesh-nodes.ts:454`), but the default implementation returns the existing promise whenever `inFlight` is set (`apps/fe/src/node/mesh-nodes.ts:305`). A throttled callback therefore does not guarantee a request after the triggering event (`apps/fe/src/node/mesh-nodes.ts:466`). Concrete scenario: the initial REST response has already captured the old membership but remains in transit for over two seconds; an unknown-node event arrives; the delayed refresh joins that old request; its stale response omits the new node, and `unknownSeen` suppresses further events until the five-minute sweep (`apps/fe/src/node/mesh-nodes.ts:490`). Queue one trailing refresh after the active request settles whenever a trigger arrives during that request. The current synchronous refresh-counter tests cannot reproduce this race.

## Should-fix

- **Continuously visible pages can retain REST-only node state for five minutes.** The fallback interval is now 300 seconds (`apps/fe/src/node/mesh-nodes.ts:369`), while events for known nodes explicitly do not refresh REST state (`apps/fe/src/node/mesh-nodes.ts:489`). The event projection does not update fields such as `loggedIn` (`apps/fe/src/node/mesh-nodes.ts:60`), which is derived from the request’s current cookies by the REST projection (`apps/gateway/src/mesh/node-list-projection.ts:208`). Concrete scenario: a remote-node session expires while the Devices page remains visible and mesh WS stays connected. No connect, visibility, or unknown-node trigger fires, so the node remains presented as signed in for up to five minutes instead of the previous 30 seconds. Preserve a short refresh path for REST-only state or invalidate the mesh list when node-scoped authentication expires.
