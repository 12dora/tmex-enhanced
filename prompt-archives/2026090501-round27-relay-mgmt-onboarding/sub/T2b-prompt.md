Findings (from a code review; verify, then fix with tests):
1. **Stale poll overwrites a successful switch.** `/api/mesh/relay/status` polling and `switchMeshRelay` (→ `POST /api/mesh/relay/switch`) both write the same store unconditionally (mesh-relay.ts ~line 124 and ~164). If a `/status` request started before the switch resolves after `/switch` succeeded, it puts the old `attached` relay back; the refresh triggered by relay-uplink-panel.tsx ~line 68 then reuses the in-flight request (`inFlight` dedupe) so nothing re-fetches and the wrong highlight can persist for a whole poll interval. Fix: add a monotonically increasing generation/revision to the store; a switch success bumps it; a poll result (success or error) is committed only if the generation it started with is still current; a refresh requested after a switch must not be satisfied by a request started before the switch (drop `inFlight` reuse across generations). Add a test that interleaves a deferred `/status` response with a `/switch` success and asserts the store keeps the switched relay.
2. **Dialog can be dismissed/re-opened while a switch is in flight.** `busy` only disables the confirm button (relay-switch-dialog.tsx ~46/56); Cancel/Escape still `dismiss()` and `request()` (use-relay-switch.ts ~44) ignores `busy`; when the first request finishes, `setTarget(null)` (~53) closes the second target's dialog. Fix: while busy, block dismiss/close/request and disable Cancel; clear `target` only if it still equals the URL the finished operation started with. Add a controller-level test (render a small harness or test the hook with a fake api) for: request A → busy → request B ignored → A resolves → target cleared; and A resolves after B was requested (if you allow that path) → B still open.
