## Background (from a read-only audit; verify in code)
- Node side (`apps/gateway/src/mesh`): `RelayUplinkClient.tearDownLink(reason)` unconditionally writes `lastConnectError` ('connect-failed', 'stopped', 'missed-pong', 'ping-failed', 'kicked:<reason>'); a successful auth/online transition (`connectWithLink`, ~line 205) never clears it. `UplinkClient.lastConnectError` (classified: dns/refused/timeout/tls/auth_rejected/protocol/aborted/http_NNN/unknown via uplink-reconnect.ts) and `UplinkPool.diagByUrl[url].lastError/lastErrorAt` (raw messages, `noteFailure`/`mergeUplinkDiag`) are likewise never cleared on success. `GET /api/mesh/relay/status` (relay-routes.ts ~line 145, relay-status-row.ts) therefore returns `online:true` together with `lastError:'connect-failed'`. The UI shows this as "最近错误 connect-failed" while the link is online — the bug we are fixing.
- Quotas (packages/shared/src/relay/codec.ts RelayQuota): maxNodes / maxStreams / bandwidthBytesPerSec. Relay server pushes control message `relay.quota` (relay-quota-ctl.ts, relay-uplink-server.ts ~line 175) with quota + currentNodes on change. Live counters exist server-side: `RelayRegistry.streamCount(tenantId)` / member activeStreams (relay-registry.ts), tenant byte rates in `RelayMetricsCollector` (relay-metrics.ts ~447, from relay-metering.ts), token bucket in relay-stream-router.ts ~125 (`TokenBucket.take()` once per forwarded chunk, while metering records the same chunk as source bytesIn and target bytesOut).
- `/api/relay/metrics.tenants[n].quota` currently returns the tenant's raw override (may be null) instead of the effective quota.
- Multi-relay: node stores several relays in `mesh_relays` (priority order); runtime has exactly one `attached`; `UplinkPool.switchTo(publicUrl)` (uplink-pool.ts ~668) exists internally (make-before-break) but there is no HTTP route. Routes list: relay-routes.ts ~line 111.

## Deliverables
1. **Current-error semantics (node side).**
   - On a successful relay/hub connection (auth ok → online) clear `lastConnectError` in `RelayUplinkClient` and `UplinkClient`, and clear the pool diag (`lastError`, `lastErrorAt`) for that URL. Keep recording failures as today.
   - Add a normalized `lastErrorCode` to `/api/mesh/relay/status.relays[n]` computed from the raw error with this closed set (already typed in packages/api-client tenant-api.ts `RelayLinkErrorCode`): `connect-failed | connect-timeout | auth-timeout | auth-rejected | heartbeat-lost | kicked | dns | refused | tls | protocol | unknown`. Mapping guidance: 'connect-failed'→connect-failed; 'connect-timeout'/'timeout'→connect-timeout; 'auth-timeout'→auth-timeout; 'auth_rejected', 'bad-token', 'token-epoch', 'unauthorized', 'bad-sig', 'member-*' close reasons→auth-rejected; 'missed-pong'/'ping-failed'→heartbeat-lost; 'kicked:*'/'tenant-kicked'/'revoked'→kicked; ECONNREFUSED/'refused'→refused; ENOTFOUND/'dns'→dns; TLS/cert errors→tls; 'protocol'/'proto-unsupported'/'client-too-old'/'ws-closed …'→protocol; 'stopped'/'aborted' → no error at all (null); anything else→unknown. Put the classifier in its own small module with a table-driven test.
   - When `online === true`, the route must return `lastError: null, lastErrorCode: null, lastErrorAt: null` for that relay (belt and braces).
   - Tests: fail → succeed → status shows no error; classifier table; pool diag cleared on success.
