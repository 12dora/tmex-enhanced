## Defect 1 — `direct enable|disable` runs in the Node CLI process but uses Bun-only APIs
- `packages/app/src/index.ts:14-29,49-67`: the `direct` command is handled inside the Node.js CLI (`dist/cli-node.js`), while `packages/app/src/commands/direct.ts:96` uses `Bun.write` and `packages/app/src/lib/native-datachannel.ts:127` uses `Bun.file`. Under Node these throw `ReferenceError: Bun is not defined`, and `direct.ts:168-198` swallows it as "direct enable skipped" with exit code 0. `init --role node` auto-direct (`init.ts:56-79`) hides the same failure.
- Fix: make the whole direct enable/disable path Node-compatible — use `node:fs/promises` (`writeFile`, `readFile`, `stat`, `mkdir`, `rm`) and `node:crypto` for sha512 instead of `Bun.*`. Check every other `Bun.` reference reachable from the Node CLI entry (`grep -rn "Bun\." packages/app/src` and trace which files are imported from `index.ts` without going through `auth-spawn`); anything reachable from Node must be portable. Files that only run under `runtime/server.js` or `runtime/cli-auth.js` (Bun targets, see `scripts/build-runtime.ts`) may keep Bun APIs.
- Exit code: `direct enable` must exit non-zero when it fails for a reason other than "platform unsupported" (unsupported platform stays a skipped/0 exit with a clear message, since `init` intentionally tolerates it). Keep `init`'s tolerant behaviour (log, don't abort) but make it print the real error message.
- Add/adjust unit tests (existing `direct.test.ts` / `native-datachannel.test.ts` if present) covering: Node-portable write+verify path, failure exit code, unsupported-platform skip.
