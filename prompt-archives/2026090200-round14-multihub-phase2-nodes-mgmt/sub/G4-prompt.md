# G4 — Standby forwards writes to the writer; best-effort enrollment-token replication

Result file: `/Users/konata/code/tmex-enhanced-wt-r14/prompt-archives/2026090200-round14-multihub-phase2-nodes-mgmt/sub/G4-result.md`

## Background
Phase 1: a standby hub rejects every write with 409 `HUB_NOT_WRITER` (`apps/gateway/src/mesh/auth-routes.ts` ~L689-715, `apps/gateway/src/hub/hub-runtime.ts` ~L314-320; uplink `key.log.append` handler `apps/gateway/src/hub/uplink-server.ts` ~L901-964). Nodes/browsers attached to a standby therefore cannot enroll, rename, revoke or append key-log records, which blocks attaching nodes to the nearest hub (next task) and makes a standby useless for onboarding while the writer is up. Enrollment tokens live only on the writer, so after a promotion, join codes issued before the crash cannot be redeemed. Exploration: `sub/EX2-result.md` §2 (token lifecycle, redeem trust path — certificate is signed by the enrollment key, not by the hub; redeem only writes `nodes`), `sub/EX1-result.md` §2 (why attach ≠ writer). Signed hub authorization: `sub/G2-result.md`; role API: `sub/G3-result.md`.

## Requirements
A. **Write forwarding on standby** (new `apps/gateway/src/hub/writer-forward.ts`):
   - For HTTP writes hitting a standby — `POST /api/hub/enrollments`, `POST /api/hub/enrollments/redeem`, `POST /api/hub/nodes/:id/rename`, `POST /api/hub/nodes/:id/revoke`, `POST /api/auth/keylog?hub=sync` (the hub-append part) — instead of 409, forward the request to the current writer's `publicUrl` over HTTPS using the same per-URL CA pin (`HubTrustStore`) that the uplink / peer poller use, carrying the caller's authentication (read how the writer authenticates these routes: node session cookie / user session; the standby must forward the credential it received, not mint one), with a 10 s timeout; return the writer's status + body verbatim (add response header `X-Tmex-Forwarded-By: <standbyHubId>`). If the writer is unknown/offline → keep today's 409 `HUB_NOT_WRITER`. Loop guard: never forward a request that already carries `X-Tmex-Forwarded-By`.
   - For the uplink `key.log.append` control frame received by a standby from an attached node: forward the record to the writer through the standby's own writer uplink (the standby is a node of the writer; reuse the node-side append path `apps/gateway/src/mesh/uplink-key-log-sync.ts` ~L512-589) and relay the ack/error back to the originating node. If the standby has no live writer uplink → today's error.
   - After a forwarded write the standby must catch up its own key log promptly (trigger the existing catch-up immediately instead of waiting for the next `node.list`).
B. **Enrollment token replication (best-effort)**: new authenticated hub-only uplink control frame `hub.tokens` (append to `UPLINK_CTL_TYPES` at the end; encode with `{ legacy: true }`-style stripping for old peers — read `packages/shared/src/uplink/codec.ts` conventions and the unknown-type behaviour ~L841-862; **only send to peers whose advertised version ≥ 1.1.13**, which you can read from the peer's `node.status`/registry version). Payload: full token rows (`id, user_id, enroll_public_key, authorization_json, authorization_sig, expires_at, used_at, node_id`) + monotonic `revision` (writer epoch, writer-local seq) + `op: upsert|tombstone`. Writer sends: full snapshot when an authorized hub uplink authenticates, then deltas on create/redeem/expire. Standby applies idempotently by `(id, revision)`; never lowers `used_at` from set to null. Redeem stays writer-only; a standby that gets promoted (role API / CLI) uses the replicated rows with the existing atomic `used_at IS NULL` consume. `POST /api/hub/enrollments` response gains `replicatedTo: string[]` (hub ids acked within 2 s; empty = not yet). Only hubs passing `isAuthorizedHub` may send or receive this frame; reject otherwise and log.
