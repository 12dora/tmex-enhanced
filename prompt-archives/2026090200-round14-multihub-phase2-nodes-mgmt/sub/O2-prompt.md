## Requirements
1. New `upgrade-batch-storage.ts`: persist the plan in `localStorage` under key `tmex.nodes.upgrade-batch.<entryNodeId>` as
   `{ schema: 1, batchId, entryNodeId, targetVersion, order: string[][] /* groups in execution order */, done: Array<{nodeId, outcome: UpgradeRunOutcome}>, startedAt, updatedAt, summaryEmitted: boolean }`.
   Pure functions: `loadBatchPlan(entryNodeId, now)`, `saveBatchPlan(plan)`, `clearBatchPlan(entryNodeId)`, `planRemaining(plan)`; every `localStorage` access wrapped in try/catch (private mode / quota) — a storage failure must never break the upgrade itself. TTL 2 hours from `updatedAt`. Invalidate when `targetVersion` differs from the current `latest` (the plan is stale) or `entryNodeId` differs.
2. Batch execution (`use-node-upgrade.ts` `startAll` / `launchUpgradeBatch` / `runUpgradeBatch`): write the plan when the batch starts; update `done` after every node settles; at the end set `summaryEmitted = true` and clear the plan (only after the summary toast). `runUpgradeBatch` gets an optional `skip: Set<nodeId>` / pre-populated `done` so a resumed batch does not re-POST nodes already finished.
3. **Resume on mount**: after the existing restore pass finishes (`restoring` becomes false) and `latest` is known, if a valid plan exists: (a) rows in the plan that are currently mid-upgrade are already being watched by the restore logic — wait for them (the batch must not double-start them: reuse `runningRef` / `resumeQueue` results); (b) rows in the plan not yet started and not `done` are started group by group in the persisted order with the same concurrency; (c) rows in `done` are counted into the summary; (d) rows that are now already at `targetVersion` count as `alreadyLatest`. When everything settles → single summary toast (using the persisted counts + the newly observed outcomes) → clear the plan. `batch` state (`running/total/completed`) must reflect the resumed batch so the UI shows progress right after refresh. The entry itself is always the last group; after the entry restarts, the page reloads and the resume path must recognise its own upgrade as `done` when `latest === current version` (read how self version is known: `row.version` for `isSelf`).
4. Cancellation semantics unchanged; if the user cancels a row inside a resumed batch it counts as `cancelled` like today. Component unmount must not clear the plan (that is the whole point), only a finished/stale batch clears it.
5. Multi-tab guard: store `ownerTabId` (random per tab, in `sessionStorage`) with a heartbeat `updatedAt`; another tab only resumes a plan whose `updatedAt` is older than 30 s (owner gone). Keep it simple; document the limitation in a comment.
6. Copy: reuse existing `nodes.upgrade.*` keys; if a new key is needed (e.g. 「已续接上次的批量升级」 info toast when resuming), add it under `nodes.upgrade.*` in zh_CN/en_US/ja_JP following `/Users/konata/code/tmex-copy-guidelines.md`, then `bun run --filter @tmex/shared build:i18n`.
