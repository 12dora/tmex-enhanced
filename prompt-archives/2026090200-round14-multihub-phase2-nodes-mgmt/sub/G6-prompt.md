## B. Opt-in auto-promote (EX1 §3)
Config `TMEX_HUB_AUTO_PROMOTE` (default off) + `TMEX_HUB_AUTO_PROMOTE_TIMEOUT_MS` (default 600_000) in `apps/gateway/src/config.ts`. In the hub peer poller (`apps/gateway/src/hub/hub-peer-poller.ts`): `/api/hub/status` response gains optional `writerView: { hubNodeId, writerEpoch, reachable, observedAt }` (this hub's freshest observation of the writer). A standby auto-promotes only when ALL hold: flag on; it is the lowest-priority (then lowest node-id) authorized standby; the writer has been unreachable from here for the full timeout (consecutive failures, no successful probe in the window); AND — when ≥3 authorized hubs exist — a strict majority of the other authorized hubs' fresh (≤2× poll interval) `writerView`s also report the writer unreachable; with exactly 2 hubs the quorum condition is waived (flag + long timeout only, this is the documented split-brain risk). Promotion reuses the role-transition machinery from G3 (`hub-role-transitions`, env write, epoch = max(all known)+1, restart) with `operationId = 'auto-<ts>'`; log loudly. Old writer returning is fenced by the existing higher-epoch logic. Tests: quorum matrix, 2-hub waiver, not-lowest-priority does nothing, fresh-view requirement, timeout reset on a single success; integration: A down long enough → B auto-promotes → A returns fenced (harness fast scheduler).
