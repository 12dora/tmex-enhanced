3. **Enroll / migrate / add / leave dialogs** (root password or passkey signing, same UX as admit-node today):
   - "接入中继": url + relay password (optional) → `POST /api/mesh/relay/enroll/proof-material` → sign proof with root key or passkey?? — the proof is an Ed25519 signature over a Borsh struct (see B1 `signRelayEnrollProof`); passkey cannot produce it, so this step requires the ROOT PASSWORD (state it in the dialog); → `POST /api/mesh/relay/enroll` → receive unsigned set-relays payload → sign key-log record (root or passkey, via the existing key-log-actions helpers with the new type) → `POST /api/auth/keylog?hub=sync` → poll status until mode = relay. Same dialog serves hub→relay migration and adding a second relay (priority appended).
   - "重新输入口令" (reauth): same flow; existing relay.
   - "离开中继": `POST /api/mesh/relay/leave/prepare` → sign → submit; danger confirm.
   - Remove one relay from the list: prepare (if B3 exposes it; else compose set-relays without it via the same prepare endpoint semantics — note in result).
4. **Add node in relay mode**: enrollment.ts creates the enrollment via `POST /api/mesh/relay/enrollments` (instead of /n/<hub>/api/hub/enrollments), fetches `GET /api/mesh/relay/join-material`, and builds the r3 join token with `encodeRelayJoinToken`; the join command shown becomes `tmex hub join <relayUrl> --token r3....` (CLI accepts it). enrollment-engine.ts: pending enrollment resolution polls `GET /api/mesh/relay/enrollments/:id` in relay mode; after signing admit-node, immediately `POST /api/mesh/relay/meta-key/prepare {op:'admit', node_id}` → sign meta-key → submit (same signer session; reuse the 5-minute grace like admit).
5. **Revoke in relay mode**: after the revoke-node record is submitted, prepare+sign+submit `meta-key {op:'rotate', exclude:[node_id]}`.
