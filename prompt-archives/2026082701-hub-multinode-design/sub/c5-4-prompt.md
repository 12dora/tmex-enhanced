# Task C5-4 — address CLI security review (packages/app + one gateway auth service method)

Context: CLI from `sub/c5-1-result.md` + wiring from `sub/c5-3-result.md`. Review: `sub/c5-1-review.md` — the coordinator judged ALL items valid with these decisions:

1. **Runtime split (blocker 2)**: the npm `bin/tmex.js` bootstrap runs under Node and must stay Node-compatible. Auth/mesh commands (`hub user *`, `hub join|leave`, `mesh reset-root`, `enroll`) must execute under the installed Bun: add a second bundle entry `packages/app/src/cli-auth-entry.ts` (Bun target, bundled by `scripts/build-runtime.ts` into `dist/runtime/cli-auth.js` next to `server.js`, included in the tarball resources the same way `server.js` is — check `bundle-resources.sh`/`build-artifacts.ts`), and make the Node CLI spawn `<installLayout.bunBin> <installDir>/runtime/cli-auth.js <args...>` with stdio inherited (TTY password prompts work) and the install env loaded from `app.env`. `index.ts` in Node only parses/dispatches; no gateway imports on the Node path. Test: a spawn-level test that runs `node packages/app/bin/tmex.js hub user add --help`-style dispatch with a fake bun path (script that echoes args) and asserts the argv forwarded; plus `bun packages/app/dist/...` smoke is done by building in the test (or skip with a clear message if build artifacts are unavailable — but do build once in the report).
2. **Join trust (blocker 3)**: never write `node_certs` from the redeem response; the trusted certs are exactly the `admit-node` projections produced by `verifyChainForJoin`. Delete the `upsertCert` loop; if the response array is kept for diagnostics, compare and reject on mismatch. Test: hub response with a tampered `node_certs` entry → local `node_certs` still equals the chain projection.
3. Head anchor (major 3): `verifyChainForJoin(records, tokenRootPk, tokenHeadHash)` semantics → the chain must **contain** a record whose hash equals `tokenHeadHash` (anchor), the final root pk must equal the token root pk, and epoch must not have changed since the anchor (any `rotate-root`/`reset-root` after the anchor → reject). Implement in `UserKeyService.verifyChainForJoin` (`apps/gateway/src/auth/user-key-service.ts`, in scope for this and item 7) with an `anchorHash` option; test: extra `set-totp` after enrollment still joins; rotate after enrollment rejected.
4. UID binding (major 4): take the uid from the verified genesis record; require certificate uid == authorization uid == `redeemed.user.id` == genesis uid before committing anything. Test with a hub returning a forged uid in `/api/auth/mode`.
5. Atomic join (major 5): fully decode + verify the redeem response in memory first, then a single DB transaction commits users/log/certs/node_identity (`UserKeyService.commitJoin(...)` — add), then write `app.env` via temp file + rename, then restart. Redeem retry: if the redeem HTTP call fails after the token was consumed, retry with the same `{certificate, cert_sig}` — the hub already returns `reused` for a consumed token; add to the hub-client a bounded retry only on network errors before the response is read.
6. HTTPS (major 2): all hub-client fetches `redirect: 'error'`; `--insecure-local` accepted only when `NODE_ENV !== 'production'`; test both.
7. Transactions for genesis + self-admit (major 8) and `hub user add` refusing existing usernames (major 7): add `UserKeyService.bootstrapUserWithSelfAdmit({username, password, identity, now})` that generates all material in memory and commits genesis + admit-node in one transaction; `hub user add` refuses if the username exists (`mesh reset-root` is the only destructive path). Tests.
8. Enroll (major 1): SIGINT sets an `AbortController` that ends the wait loop and prints the Nodes-page hint; hub role polls the local `nodes` table for a node whose enrollment token id matches (the hub redeem stores `node_id` on the token via `consumeEnrollmentToken`) and reads `{certificate, cert_sig}` — add persistence of the redeemed certificate on the hub side: `enrollment_tokens` gets no new column; instead store `certificate_b64`/`cert_sig_b64` inside `authorizationJson` alongside `entry_node_id` when redeeming (`apps/gateway/src/hub/hub-runtime.ts` is out of scope — write the exact patch in the report; implement the CLI polling against that JSON shape and test with a fake row). Non-hub role: poll hub `GET /api/hub/nodes` (add `certificate`/`cert_sig` to that response in the report as a required hub change) — until then it uses the same polling function with a fetcher.
9. TOTP in enroll (major 6): read `totpEnabled` from `/api/auth/mode`; prompt for the code, derive `k_totp` from the seed with the current epoch, send `{code, k_totp}`, drop the seed after. Test with a fake node requiring TOTP.
10. `hub user reset` (major 9): stop the service before wiping, restart after (using `restartService` / service stop), and also mark all `node_certs` of the user as revoked? No — design says reset clears the registry only; keep certs but document that revoked nodes must be `revoke-node`d. Just do stop→wipe→start and test the ordering with a fake service.
