## Product decision
A machine joins an existing Hub mesh with **Hub URL + the mesh account password** (no join token typed by the user). Protocol (方案一): the joining client fetches `GET <hub>/api/auth/mode` (uid + kdfParams, unauthenticated), derives the root key from the password, creates a normal enrollment locally (`createEnrollment(rootKey)` → enrollSk + root-signed authorization), signs a proof with a NEW domain `tmex/hub-enroll/v1` = `domain ‖ hub_host ‖ uid ‖ root_public_key ‖ enroll_pk ‖ ts(u64)` (±5 min window; new shared module `packages/shared/src/auth/hub-enroll-proof.ts` + test), and calls `POST /api/hub/enrollments/by-password` `{ proof:{bytes,sig}, enroll_pk, authorization, authorization_sig, exp }` — no node-session. The hub verifies the proof against the user's current root public key (single-user hub: resolve the user by uid inside the proof), verifies the authorization with the existing `verifyEnrollmentAuthorization`, then creates the enrollment exactly like `POST /api/hub/enrollments` (same writer-ownership / standby forwarding / replication — put the handler in a NEW file `apps/gateway/src/hub/hub-password-enroll.ts`, hub-runtime.ts is at the allowlist limit; only add the dispatch line there, before the `/api/hub/enrollments/:id` dynamic route) and returns the same material the token path would give the client (enrollment id/token, hub url, CA fingerprint …) so the client continues with the unchanged `performHubJoin()` using its own enrollSk. Rate limit: new `apps/gateway/src/hub/hub-enroll-limiter.ts` built on `auth-login-limiter.ts` (sliding window; key = ip + uid; count proof failures; also cap successful creations per uid per hour). Never log proof/password material. Tests in `hub-runtime.test.ts` / new `hub-password-enroll.test.ts` / `writer-forward.test.ts`: happy path, wrong password, expired ts, limiter, standby forwards to writer.
